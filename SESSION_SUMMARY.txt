OVERVIEW
--------
A system that monitors access to sensitive credential/config artifacts (.aws,
.ssh, .azure, .kube, .steampipe) on Linux servers. Instead of treating all
access as malicious, it establishes a baseline of normal behavior and will
(eventually) flag deviations with explainable risk scores.

ARCHITECTURE (Current)
-----------------------
  Filesystem Access Event
         |
  collector.py  (watchdog/inotify)  <-- reads policy.yaml for paths
         |
  auditd_integration.py  (primary: kernel-level audit, zero race condition)
  proc_scanner.py        (fallback: /proc scan, race-prone)
         |
    SQLite (events table)  — PID, process, user fields populated
         |
  baseline.py   (computes profiles by artifact+user+process)
         |
    SQLite (baseline table)
         |
    [NOT BUILT YET] anomaly_detector.py  (compares new events vs baseline)

FILE STRUCTURE
--------------
policy.yaml            — Artifact definitions (paths to monitor)
artifact_scan.py       — TUI file browser for selecting artifacts to monitor
requirements.txt       — Dependencies: watchdog>=4.0, pyyaml>=6.0

proc_scanner.py        — /proc-based process resolver (fallback)

baseline.py            — Computes normal behavior profiles from collected events

DEPENDENCIES
------------
- Python 3.x

- pyyaml 6.0.3 (YAML parsing for policy.yaml)
- sqlite3 (stdlib, no install needed)

- Sudoers configured: debian ALL=(root) NOPASSWD: /usr/sbin/auditctl, /usr/sbin/ausearch

DATABASE SCHEMA (db.py)
-----------------------
Table: events
  id              INTEGER PRIMARY KEY AUTOINCREMENT
  timestamp       TEXT NOT NULL          -- ISO-8601 UTC
  artifact_path   TEXT NOT NULL          -- which sensitive path was accessed
  access_type     TEXT NOT NULL          -- read, write, create, delete, moved
  pid             INTEGER               -- populated via auditd or /proc
  process_name    TEXT                  -- populated via auditd or /proc
  ppid            INTEGER               -- populated via /proc
  parent_process_name TEXT              -- populated via /proc
  user_id         INTEGER               -- populated via auditd or /proc
  username        TEXT                  -- populated via auditd or /proc
  INDEXES: idx_events_artifact, idx_events_timestamp, idx_events_user

Table: baseline
  id                  INTEGER PRIMARY KEY AUTOINCREMENT
  artifact_path       TEXT NOT NULL
  user_id             INTEGER NOT NULL
  process_name        TEXT NOT NULL
  access_count        INTEGER NOT NULL DEFAULT 0
  first_seen          TEXT NOT NULL
  last_seen           TEXT NOT NULL
  normal_hours        TEXT               -- JSON array, e.g. "[4,9,14]"
  avg_access_interval REAL               -- seconds between accesses
  created_at          TEXT NOT NULL
  UNIQUE INDEX: (artifact_path, user_id, process_name)

HOW TO RUN
----------
# 1. Activate environment
source venv/bin/activate

# 2. Define what to monitor (TUI browser)
python artifact_scan.py
#   Navigate with arrow keys
#   Space to select files/dirs
#   S to save policy.yaml
#   Q to quit

# 3. Start collecting events (runs until Ctrl+C)
python collector.py

# 4. In another terminal, generate some events (writes are detected)
echo "# update" >> /home/debian/.azure/config

# 5. Compute baseline
python baseline.py          # compute and show
python baseline.py --show   # view without recomputing
python baseline.py --reset  # clear and recompute

POLICY.YAML FORMAT
------------------
version: 1
monitoring:
- path: /home/debian/.azure
  type: directory
  recursive: true
  category: user_defined

PROC_SCANNER.PY DETAILS
-----------------------
- Scans /proc/*/fd/ symlinks to find which process has a target file open
- Returns ProcessContext(pid, comm, ppid, parent_comm, uid, username)
- On each inotify event, collector triggers scan_for_file(src_path)
- Fills in PID, process name, parent process, user fields
- Race condition: quick open/close (e.g. cat file) may not be caught
- For sustained access (tail, curl, ssh), detection is reliable
- Also supports scan_for_paths() for multi-target efficiency

AUDITD_INTEGRATION.PY DETAILS
-----------------------------
- Uses auditctl (via sudo) to add file watch rules (kernel-level)
- Uses ausearch (via sudo) to read audit events (zero race condition)
- Shared audit key: "artifact_watch_all" (all collector instances use same key)
- Uses _run_audit() helper that prefixes all commands with sudo
- Parses audit log output using state-machine:
  * Splits on '----' separators into event blocks
  * Groups SYSCALL, CWD, PATH, PROCTITLE records per event
  * Extracts PID, process name, UID, syscall, exe from SYSCALL records
  * Resolves relative PATH names using CWD
  * Skips auditd's own events (auditctl, audispd, auditd processes)
- Retries up to 5 times with 0.5s delays (auditd may not flush immediately)
- Detects if auditd is installed and running (graceful fallback)
- Cleans up audit rules on collector shutdown (remove_watches)
- Handles both quoted and unquoted ausearch field formats
- Handles numeric and username UID formats (-i flag)

COLLECTOR.PY DETAILS
--------------------
- Loads monitoring targets from policy.yaml
- Uses watchdog Observer + inotify to watch paths
- At startup, checks if auditd is available:
  * If yes AND rules install successfully: uses AuditdResolver as primary
  * If rules fail (no sudo): falls back to ProcScanner (/proc scanning)
  * If auditd not installed: uses ProcScanner only
- On any filesystem event:
  * Maps watchdog event type to access_type (read/write/create/delete/moved)
  * Matches event path against monitored artifacts (prefix matching)
  * Resolves process: auditd first, then /proc fallback if auditd returns None
  * Inserts event into SQLite with full process/user context
- On shutdown: removes audit rules if auditd was used

BASELINE.PY DETAILS
-------------------
- Reads all events from SQLite
- Groups by (artifact_path, user_id, process_name)
- For each group computes:
  * access_count: total number of events
  * first_seen / last_seen: time range
  * normal_hours: hours of day with >=10% of accesses (JSON array)
  * avg_access_interval: mean seconds between consecutive accesses
- Upserts into baseline table (deduplicates on the triple key)
- CLI: python baseline.py [--reset] [--show]

DESIGN PRINCIPLES
-----------------
1. Context over content — accessing .azure/config isn't inherently malicious;
   who, when, and in what sequence determines risk.
2. Explainability — risk scores must be interpretable, not black-box.
3. Low false-positive rate — production apps legitimately touch these files.
4. Sequence-awareness — single access is low-signal; a chain of accesses is
   high-signal.
